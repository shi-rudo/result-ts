# Version 2 Migration

Version 2 removes the APIs that 1.x deprecated. Each removed API has a replacement that 1.x already exports, so you can migrate before you upgrade. After the upgrade, the TypeScript compiler reports every use of a removed API in typed code.

## Breaking Changes

<!-- The "Removed in 2.0" section of skills/result-ts/references/api-cheatsheet.md mirrors this list. Update both. -->

- Version 2 requires Node.js 22 or later. Node.js 20 has reached its end of life. Stay on 1.2.x for Node.js 20.
- Version 2 removes `fromSerialized()`. Validate the payload, then rebuild the Result with `ok`/`err`.
- Version 2 removes the `.serialize()` method. Use `.toSerialized()`, which returns a different shape.
- Version 2 removes `unwrapOrDefault()`. Use `unwrapOr()`.
- Version 2 removes `ERR_INVALID_STATE`. Use `ERR_INVALID_RESULT_STATE`.
- Version 2 removes the `.match()` method of a Result. Use `.matchError()`.
- The `MatchOnOkError` constructor requires the name of the method that was called on an `Ok`.
- `sequenceRecord()` rejects an array or a tuple at compile time. Such a call always threw `InvalidResultStateError`. Use `sequence()` for a list. Narrow an argument typed as a union of an array and a record with `Array.isArray()` first.
- Version 2 removes the aliases `bimap`, `all`, `Result.all` and `gen`. Use `mapBoth`, `sequence`, `Result.sequence` and `task`.
- `ResultType<T, E>` is now `SerializedResult<T, E>`.
- `matchErr()` / `matchErrAsync()` are now `matchErrorToResult()` / `matchErrorToResultAsync()`. The builder types, the error class and its code follow: `ErrorToResultMatchBuilder`, `AsyncErrorToResultMatchBuilder`, `MatchHandlerNotResultError`, `ERR_MATCH_HANDLER_NOT_RESULT`.
- Version 2 removes the operators `match`, `matchAsync`, `mapOr` and `mapOrElse`. Use `fold` and `foldAsync`: `mapOr(r, d, f)` is `r.fold(f, () => d)`, and `mapOrElse(r, onErr, onOk)` is `r.fold(onOk, onErr)`.
- `sequenceRecord()` leaves out a key that holds `undefined` instead of throwing. Other values that are no `Result` still throw.

## Rebuilding a Result from a Payload

Before:

```ts docs-check:skip
import { fromSerialized } from '@shirudo/result';

const restored = fromSerialized<User, ApiError>(JSON.parse(body));
```

After:

```ts
import { err, ok, type Result, type SerializedResult } from '@shirudo/result';

type User = { id: number };
type ApiError = { code: 'not-found' };

// Your schema step (Zod, Valibot, or a hand-written guard) owns the payload types.
declare function validate(input: unknown): SerializedResult<User, ApiError>;

const body = '{"_tag":"Ok","value":{"id":1}}';
const parsed = validate(JSON.parse(body));
const restored: Result<User, ApiError> = parsed._tag === 'Ok' ? ok(parsed.value) : err(parsed.error);
```

`fromSerialized()` checked only the envelope, never the payload. Its type parameters still claimed `T` and `E` for any payload. Your schema step checks the payload, so the types of the rebuilt Result are true. If you caught `InvalidResultStateError` around `fromSerialized()`, handle the failure of your schema step there.

## Serializing a Result

`.toSerialized()` returns `{ _tag: 'Ok', value }` or `{ _tag: 'Err', error }`. `JSON.stringify` writes the same shape for the Result itself. `.serialize()` returned `{ isSuccess, data?, error? }`, so read the state from `_tag` instead of `isSuccess`.

Before:

```ts docs-check:skip
const wire = result.serialize(); // { isSuccess: true, data: 42 }
if (wire.isSuccess) console.log(wire.data);
```

After:

```ts
import { ok, type Result } from '@shirudo/result';

const result: Result<number, string> = ok(42);

const wire = result.toSerialized(); // { _tag: 'Ok', value: 42 }
if (wire._tag === 'Ok') console.log(wire.value);
```

If a receiver still reads the old shape, build that shape with `.fold()`:

```ts
import { ok, type Result } from '@shirudo/result';

const result: Result<number, string> = ok(42);

const legacy = result.fold(
    data => ({ isSuccess: true as const, data }),
    error => ({ isSuccess: false as const, error }),
);
```

`.toUserFriendly()` also returns `isSuccess` and `data`, but it converts the error to a string. It does not replace `.serialize()`.

## Replacing `unwrapOrDefault()`

Before:

```ts docs-check:skip
import { unwrapOrDefault } from '@shirudo/result';

const port = unwrapOrDefault(parsed, 8080);
```

After:

```ts
import { err, unwrapOr, type Result } from '@shirudo/result';

const parsed: Result<number, string> = err('not a number');

const port = unwrapOr(parsed, 8080);
```

`unwrapOr()` takes the same arguments and returns the same value. The name `unwrapOrDefault` suggested the `unwrap_or_default` of Rust, which takes no argument.

## Replacing `ERR_INVALID_STATE`

Before:

```ts docs-check:skip
import { ERR_INVALID_STATE, ResultError } from '@shirudo/result/errors';

const isInvalidState = (error: unknown) => error instanceof ResultError && error.code === ERR_INVALID_STATE;
```

After:

```ts
import { ERR_INVALID_RESULT_STATE, ResultError } from '@shirudo/result/errors';

const isInvalidState = (error: unknown) => error instanceof ResultError && error.code === ERR_INVALID_RESULT_STATE;
```

Both constants held the string `'ERR_INVALID_RESULT_STATE'`. A comparison against that string literal keeps working, and only the import changes.

## Replacing `.match()`

Before:

```ts docs-check:skip
if (result.isErr()) {
    const message = result
        .match()
        .when(NetworkError, () => 'Retry later')
        .otherwise(error => `Unexpected error: ${error.message}`);
}
```

After:

```ts
import { Result } from '@shirudo/result';

class NetworkError extends Error {
    readonly code = 'network';
}
class ValidationError extends Error {
    readonly code = 'validation';
}

const result: Result<string, NetworkError | ValidationError> = Result.err(new NetworkError('timeout'));

if (result.isErr()) {
    const message = result
        .matchError()
        .when(NetworkError, () => 'Retry later')
        .otherwise(error => `Unexpected error: ${error.message}`);
}
```

`.matchError()` returns the same builder that `.match()` returned. To handle both `Ok` and `Err`, use `fold`.

## Constructing `MatchOnOkError`

The constructor of `MatchOnOkError` requires the name of the method that was called on an `Ok`. Its default was `'match'`, the name of the removed method. This change affects only code that constructs the error itself, for example a test double.

```ts
import { MatchOnOkError } from '@shirudo/result/errors';

const error = new MatchOnOkError('matchError');
```
